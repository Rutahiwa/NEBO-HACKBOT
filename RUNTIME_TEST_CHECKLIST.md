# NEBO-HACKBOT Runtime Test Checklist

Specific test flows to validate each phase of the fork on the GPU VM. Run these against OWASP Juice Shop (or an equivalent deliberately vulnerable target).

---

## Phase A: Context Efficiency

Validates that tool output truncation and execution context abbreviation reduce token usage per agent call.

- [ ] Run a Juice Shop flow (e.g., "Find and exploit vulnerabilities in http://juiceshop:3000"). Monitor token count per agent call in the Langfuse dashboard or backend logs. Token count per call should be noticeably lower than baseline PentAGI on the same flow.
- [ ] Verify tool results in the UI are truncated for large outputs. Run a command that produces verbose output (e.g., `nmap -sV -p- <target>`) and confirm the stored tool result shows approximately 8 KB head + 2 KB tail with a `[... truncated N bytes ...]` marker in between.
- [ ] Run a multi-subtask flow (5+ subtasks). In the agent prompt for later subtasks, verify the execution context shows abbreviated older subtasks (short summaries) rather than full verbatim output from every prior subtask.

---

## Phase B: CLI-Operator Behaviour

Validates that agents behave as CLI operators -- using terminal commands and tool calls instead of narrating GUI tool usage.

- [ ] Run a Juice Shop flow. Review agent logs (message fields in the flow detail view). Confirm there are NO references to Burp Suite, OWASP ZAP, or any GUI-based security tool. Agents should use CLI equivalents: `nmap`, `sqlmap`, `ffuf`, `httpx`, `curl`, `nikto`, etc.
- [ ] Check that agent message fields (the `message` column in flow logs / GraphQL `message` fields) are under 200 characters. Agents should be concise, not writing essay-length explanations.
- [ ] Verify agents produce tool calls (function calls to `terminal`, `browser`, `web_search`, `recon`, `injection`, etc.) in most responses rather than plain-text narration. A response that only contains text without a tool call is acceptable occasionally (e.g., for planning), but the majority of agent turns should include at least one tool call.

---

## Phase C: Context Architecture

Validates the sliding-window context system and chain pruning.

- [ ] Run a long flow (10+ subtasks) with `USE_CONTEXT_WINDOW=true` and `CONTEXT_WINDOW_SIZE=10` (defaults). Measure agent call round-trip times. They should be significantly lower than baseline PentAGI on the same flow, because the LLM receives fewer tokens per call.
- [ ] Set `USE_CONTEXT_WINDOW=false` in `.env` and restart the backend. Run the same flow. Verify it still completes successfully (the full chain is sent to the LLM, matching original PentAGI behavior). This validates the fallback path.
- [ ] Set `USE_CONTEXT_WINDOW=true` with `CONTEXT_WINDOW_SIZE=5` (tighter window). Run a medium flow (5-8 subtasks). Verify the flow still completes and agents do not lose critical context. Check that earlier messages are indeed dropped from the LLM call (visible in debug logs or Langfuse traces).
- [ ] Verify chain pruning is active: in a flow with many tool calls, check that stale tool results (older than the 5 most recent) are replaced with short stubs containing `[... pruned N bytes ...]`. This is handled by `pruneStaleToolResults` in `backend/pkg/providers/chain_pruning.go`.

---

## Phase D: Specialist Agents

Validates that the Primary Agent delegates to specialist agents and each specialist performs its designated task.

- [ ] Run a Juice Shop flow. Verify the Primary Agent (`primary_agent.tmpl`) delegates to specialist agents by calling their tool names: `recon`, `injection`, `xss_test`, `auth_test`, `idor_test`, `ssrf_test`.
- [ ] Verify the **recon specialist** runs reconnaissance tools: `nmap`, `httpx`, `ffuf`, `nikto`, `whatweb`, `gobuster`, or similar. It should NOT run exploitation tools (that is the job of injection/xss/etc. specialists).
- [ ] Verify the **injection specialist** uses `sqlmap` or manual SQL injection payloads for SQLi testing. It should focus on injection vulnerabilities (SQLi, command injection, template injection), not general scanning.
- [ ] Verify the **XSS specialist** tests for cross-site scripting using `curl`, the headless browser tool, or crafted payloads. It should probe reflected/stored/DOM XSS vectors.
- [ ] Verify the **auth specialist** tests authentication and session management: default credentials, session fixation, brute force, JWT issues.
- [ ] Verify the **IDOR specialist** tests access control: horizontal/vertical privilege escalation, direct object reference manipulation.
- [ ] Verify the **SSRF specialist** tests server-side request forgery vectors: internal network access, cloud metadata endpoints, URL scheme abuse.
- [ ] Verify each specialist's result appears in the flow report. The Primary Agent should aggregate specialist findings into the final task/flow report generated by the reporter agent (`reporter.tmpl`).

---

## Phase E: Validation Agent

Validates that the findings validator independently reproduces and filters candidate vulnerabilities.

- [ ] Manually trigger a finding that the validator should REJECT. Example: submit a self-XSS finding (XSS that only fires in the attacker's own session) or a false positive from a scanner. The validator agent (`validator` tool) should attempt to reproduce it independently and mark it as REJECTED if it cannot confirm exploitability.
- [ ] Verify the validator independently reproduces confirmed findings. For a real vulnerability (e.g., SQL injection in Juice Shop's search field), the validator should execute its own proof-of-concept (separate from the original specialist's test) and confirm the finding.
- [ ] Verify REJECTED findings do not appear in the final report. After the validator marks a finding as rejected, the reporter agent should exclude it from the final output.
- [ ] Verify the validator assigns severity assessments. Confirmed findings should include a severity rating (Critical/High/Medium/Low/Info) based on the validator's independent assessment, not just the original specialist's claim.

---

## Baseline Comparison

Run a controlled comparison between original PentAGI and the NEBO-HACKBOT fork.

### Setup

- [ ] Deploy original PentAGI (unmodified v2.1.0 base) against the same Juice Shop instance
- [ ] Deploy NEBO-HACKBOT fork against the same Juice Shop instance
- [ ] Use the same LLM (Qwen2.5-72B-AWQ via vLLM) for both runs
- [ ] Use the same flow prompt for both runs (e.g., "Perform a comprehensive penetration test of http://juiceshop:3000")

### Metrics to record

| Metric | Original PentAGI | NEBO-HACKBOT | Notes |
|---|---|---|---|
| Total flow time (wall clock) | | | End-to-end from flow start to report |
| Total token count (input + output) | | | Sum across all agent calls |
| Number of findings | | | Raw count before validation |
| Number of confirmed findings | | | After validator filtering (NEBO-HACKBOT only) |
| False positive rate | | | Findings that are not actually exploitable |
| Number of agent calls | | | Total LLM API calls across all agents |
| Average tokens per agent call | | | Total tokens / number of calls |
| Number of subtasks created | | | Subtask count from the planner |

### Expected outcomes

- NEBO-HACKBOT should use fewer total tokens (context windowing + chain pruning + tool output truncation)
- NEBO-HACKBOT should have a lower false positive rate (validator agent filters non-reproducible findings)
- NEBO-HACKBOT should produce more focused findings (specialist agents target specific vulnerability classes)
- Wall clock time may be similar or slightly longer due to validation overhead, but token efficiency should be substantially better

---

## Environment Notes

- All tests should be run on the GPU VM (2x A100 40GB, Debian 13)
- vLLM with `--tensor-parallel-size 2` and `--enable-prefix-caching`
- Juice Shop should be deployed in a Docker container on the same network as the NEBO-HACKBOT stack
- Enable Langfuse (`docker-compose-langfuse.yml`) for token usage tracking if available
